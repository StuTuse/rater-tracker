## 预定构建与签名流程

采用GitHub托管Windows runner从固定源码提交重新构建，使用锁文件和`npm ci`，先运行`npm run check`。本地旧包可用于服务方了解文件结构，不能直接冒充受验证CI产物；Foundation的GitHub来源验证要求签名前相关工作流任务均由GitHub托管runner执行。[官方GitHub集成](https://docs.signpath.io/trusted-build-systems/github)

当前锁定electron-builder **26.15.3**，自定义签名入口为`win.signtoolOptions.sign`；签名散列拟只设`sha256`。保留元数据编辑和`forceCodeSigning=true`。不能照抄v27的配置，也不能关闭`signAndEditExecutable`而丢失图标／品牌。已核对本地锁定实现：主EXE先编辑资源再签名，NSIS会先生成／签卸载器，再将其嵌入最终安装程序。

目标顺序：

1. 从目标提交构建应用，完成图标、产品名、作者、版本等编辑。
2. 仅对服务方批准的本项目文件提出签名请求；上传到GitHub Actions artifact，使用其真实artifact ID提交SignPath，人工批准后取回并在原路径替换。取回文件先验签再继续打包。
3. NSIS生成卸载器后，对卸载器执行同样的上传、批准、下载和验签，保证嵌入的是已签名卸载器。
4. NSIS完成包含已签应用／卸载器的安装程序，再签最终Setup。不能只签Setup外壳，也不能在签后继续修改PE资源或重打包同一文件。
5. 验证安装后的主EXE和卸载器与对应已签输入一致，随后产生最终SHA-256，按现有双平台Release规则发布。Android继续原证书，不迁移至Foundation证书。

实现接入时需要编写electron-builder自定义签名hook与GitHub artifact／官方提交动作的衔接，并验证等待、超时和失败中止。官方Action不能直接作为Node函数调用；上述顺序是待实现设计，不是现成可执行工作流。需先用服务方测试策略跑通三个阶段及人工批准次数，再启用正式策略。若服务不接受当前Electron主EXE签名范围，先调整经批准的构建／打包方式，不缩减为只签外壳。

NSIS安装程序本身是PE文件；官方复合格式列表未列NSIS的内部重签能力，因此本方案不依赖一次请求自动解包并签内部文件。依据：[SignPath文件格式与元数据约束](https://docs.signpath.io/artifact-configuration/reference)、[electron-builder v26 Windows配置](https://www.electron.build/v26/docs/win/)、[v26签名参数](https://www.electron.build/v26/docs/features/code-signing/code-signing-win/)。

## 获批后需要配置的项目

以下为正式签名参数规划，所有真实值由服务方项目配置产生；目前没有创建SignPath Secret或安装SignPath App。用户同意补充GitHub CLI workflow权限，仅用于启用未签名样包CI；该CI不调用SignPath，运行结果以W058为准。

| 位置 | 名称／要求 |
| --- | --- |
| GitHub Secret | `SIGNPATH_API_TOKEN`：仅给该项目／策略的提交权限，不保存私钥 |
| GitHub Variables | `SIGNPATH_ORGANIZATION_ID`、`SIGNPATH_PROJECT_SLUG`、`SIGNPATH_SIGNING_POLICY_SLUG`：均用实际获批值 |
| SignPath | 各阶段artifact配置slug、精确文件白名单、产品名与版本约束；不用任意`*.exe`／`*.dll`批量重签 |
| GitHub来源绑定 | 按官方集成绑定仓库、工作流和GitHub托管runner；需要App时只授权本仓库 |
| 工作流权限 | 构建／签名任务仅`contents: read`、`actions: read`；发布任务单独申请`contents: write` |
| 触发与批准 | 从主分支人工发起，绑定固定提交；正式签名保留服务方人工批准；PR尤其fork不取得签名令牌 |
| Action版本 | 启用前审核并固定Action提交SHA；当前官方示例为SignPath提交动作v3与upload-artifact v7，不直接将移动tag作为最终可信边界 |
| 文件约束 | ProductName为Rater & Tracker、CompanyName为TuseCreation，逐阶段核对实际PE版本；现有alpha.21的数值ProductVersion为0.1.0.0，不能将alpha字符串直接用于全部PE字段 |
| 证书身份 | 记录服务方实际生产证书的公开指纹／主体；hook的publisherName使用证书身份，不填TuseCreation冒充 |

artifact默认ZIP上传时，SignPath artifact配置根元素须为`zip-file`。正式XML由各阶段真实样包生成，再人工收窄文件范围和元数据约束，并由服务方校验；本轮没有提交未经服务验证的XML或工作流。

## 签名交付验收

启用后必须核对Setup、实际安装主EXE、卸载器三处的Authenticode有效性、批准的证书身份及可信时间戳，并以Windows SDK SignTool复核；缺签、错误主体／指纹、未批准、超时或下载损坏均停止发布。`forceCodeSigning`不能替代最终验签，尤其自定义hook仅返回成功时，打包器并不能证明服务真的签过。

另在隔离Windows环境检查安装、旧未签名版升级、桌面快捷方式目标、卸载和数据保持。当前“开发验收”快捷方式使用未签名源码Electron；正式交付应使用已签名安装版创建的快捷方式。首次联网下载后的SmartScreen表现单独记录，不将本机无警告扩大为全体用户结论。

正式签名流水线与安装检查待服务获批和实际实现后执行。现已提供[手动样包工作流](../.github/workflows/windows-signing-sample.yml)，用于生成带GitHub来源信息的未签名样包；实际状态见W058。用户已选择自行在申请表填写姓名和邮箱；申请尚未提交，MFA、完整许可审计、安装披露及服务方签名范围审核仍待完成。
